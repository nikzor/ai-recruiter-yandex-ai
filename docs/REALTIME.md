# Непрерывное интервью через Realtime API

## Сценарий и план внедрения

Realtime — отдельный режим голосового интервью без ручной отправки реплик. Пользователь выбирает уровень, нажимает «Начать интервью» и разрешает микрофон. Вопросы, ответы и уточнения идут в одном непрерывном разговоре. Во время разговора единственная кнопка управления — «Завершить интервью». По завершении появляется отчёт.

| Этап | Реализация | Критерий |
| --- | --- | --- |
| Контракт поставщика | Серверный WebSocket к Yandex Realtime, отдельные права и речевая модель | Ключ остаётся на сервере, форматы аудио согласованы |
| Серверный сценарий | Сохранение ответа по VAD, уточнение либо следующий вопрос, автоматический отчёт | До пяти основных вопросов, не более одного уточнения на каждый, последовательная revision |
| Клиент | Подготовка микрофона при старте, один WebSocket на всё интервью, потоковое аудио и перебивание | Между вопросами не нужны нажатия; нет редактора, ручной отправки и переключения режима |
| Завершение и восстановление | Завершение всего интервью, частичный отчёт, повтор подключения или отчёта | Сбой не стирает сохранённые ответы; пустое интервью не получает выдуманную оценку |
| Проверки | Локальные тесты транспорта и сценария, сборка, отдельный облачный smoke | Результаты новой реализации и физического устройства фиксируются отдельно |

## Кто управляет интервью

Источник истины — серверная сессия. `server/provider.mjs` через Chat Completions создаёт основные вопросы, решает, нужно ли уточнение, и формирует итоговый отчёт. Realtime расшифровывает микрофон и определяет паузы. По умолчанию готовые вопросы озвучивает SpeechKit TTS v1: Каждый вопрос передаётся одним MP3 и декодируется браузером целиком, без повторной генерации текста речевой моделью и без стыков PCM-фрагментов. Речевая модель не выставляет оценки и не выбирает следующий этап самостоятельно.

Основные темы — Dart, виджеты, состояние, данные, качество. `provider.nextTurn` одним запросом возвращает `{action: "followup" | "question" | "finish", question}`: уточнение, следующий основной вопрос или завершение. Отдельных последовательных запросов на решение об уточнении и генерацию следующего вопроса нет. После ответа на него сервер переходит к следующему основному вопросу. Уточнение учитывается вместе с основным ответом и не добавляет шестую оценку.

После пяти вопросов отчёт создаётся автоматически. Ручное завершение оценивает только обсуждённые вопросы: от 1 до 5 оценок, итог `round(sum / (count * 4) * 100)`. Без ответов сессия завершается с `report: null`. При ошибке генерации состояние `ready` позволяет повторить отчёт, сохраняя историю.

## Клиентский жизненный цикл

| Модуль | Назначение |
| --- | --- |
| [`src/RealtimeAnswer.jsx`](../src/RealtimeAnswer.jsx) | Статус, расшифровка только для чтения и завершение интервью |
| [`src/useRealtimeInput.js`](../src/useRealtimeInput.js) | `prepareRealtimeInput`, микрофон, WebSocket, обновление сессии и очистка |
| [`src/audio/realtime-playback.mjs`](../src/audio/realtime-playback.mjs) | Потоковый PCM-плеер и остановка очереди при речи пользователя |

Кнопка старта синхронно создаёт/разблокирует AudioContext и запрашивает микрофон до ожидания HTTP создания сессии. После готовности сессии подключение начинается автоматически. Микрофон открыт, но чанки не передаются до серверного `ready`. Компонент сохраняет один экземпляр по ID сессии между всеми вопросами.

Исходящий поток — AudioWorklet, PCM16 little-endian mono 16 кГц, обычно 100 мс на чанк. По умолчанию один MP3 вопроса декодируется браузером целиком и воспроизводится одним AudioBufferSourceNode. Только нативный режим использует очередь PCM16. Начало речи очищает очередь и прерывает озвучивание. Канонический вопрос отображается отдельно; инструкция на дословное озвучивание сама по себе не гарантирует качество произношения.

Пауза завершает реплику автоматически. UI показывает подготовку следующего вопроса, затем продолжает слушать; редактора и подтверждения текста нет. «Завершить интервью» останавливает микрофон с flush последнего кадра, прекращает озвучивание и ждёт итоговую сессию. Клиентский таймаут ожидания итога — до 120 секунд.

После перезагрузки вкладки микрофон не включается автоматически: нужен один клик «Продолжить разговор». При разрыве можно переподключиться либо завершить интервью через запасной HTTP-маршрут по сохранённой части. Автоматического переключения на клавиатуру или обычный голосовой режим нет.

Ошибка, завершение и размонтирование закрывают WebSocket, микрофонные tracks, AudioContext и таймеры. Разрешение на микрофон, пришедшее после отмены, также закрывается.

## Облачная конфигурация

Все настройки читает сервер; переменные `VITE_*` для ключа не используются.

```dotenv
AI_MODE=yandex
API_KEY=ваш_ключ
YANDEX_FOLDER_ID=идентификатор_каталога
REALTIME_ENABLED=true
REALTIME_MODEL=speech-realtime-deepseek-v4-flash
REALTIME_VOICE=filipp
REALTIME_TTS=speechkit
```

`API_KEY` имеет приоритет над запасным `YANDEX_API_KEY`. По умолчанию Realtime включён при явном `AI_MODE=yandex`, непустом ключе и Folder ID; строка `REALTIME_ENABLED=false` отключает его. Модель по умолчанию — `speech-realtime-deepseek-v4-flash`; можно указать имя или полный URI `gpt://<folder_id>/<model>`. В нативном режиме голос `REALTIME_VOICE` по умолчанию — `filipp`; быстрый режим использует `TTS_VOICE`.

Нужны роль сервисного аккаунта **`ai.models.user`** и область API-ключа **`yc.ai.foundationModels.execute`**. Это отдельная проверка доступа; успешные вызовы Chat Completions или SpeechKit её не заменяют. Права, модель и endpoint приведены в [официальной инструкции голосового агента](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/agents/create-voice-agent).

Облачный WebSocket:

```text
wss://ai.api.cloud.yandex.net/v1/realtime/openai?model=gpt://<folder_id>/speech-realtime-deepseek-v4-flash
Authorization: Api-Key <server_key>
```

Контракт поставщика — [Yandex Realtime API](https://aistudio.yandex.ru/ru/docs/ai-studio/realtime/). `STT_ENABLED` не управляет Realtime. `TTS_ENABLED` включает быстрый синтез SpeechKit; при его отключении применяется нативное озвучивание Realtime.

## Подключение и сохранение

| Модуль | Назначение |
| --- | --- |
| [`server/realtime.mjs`](../server/realtime.mjs) | Авторизация, конфигурация облачной сессии и непрерывный ресемплер 16 → 44.1 кГц |
| [`server/realtime-socket.mjs`](../server/realtime-socket.mjs) | Допуск браузера, VAD, последовательное продвижение интервью, синтез и итог |

```text
ws://127.0.0.1:<PORT>/api/speech/realtime?sessionId=<id>&revision=<revision>
```

На HTTPS используется `wss`. `/api/health` возвращает `speech.realtimeEnabled`: это готовность конфигурации, а не проверка облачных прав. Допуск WebSocket требует допустимый Origin, неистёкшую сессию, статус `active`, актуальную revision и отсутствие конфликтующей операции. `realtimeBusy` блокирует параллельные HTTP-изменения и речевые операции.

Сервер хранит историю, обновляет revision и передаёт новое публичное состояние в событии `session`; UI обновляет текущий вопрос без пересоздания микрофона. Финальное событие `done` содержит сессию с результатом. При ошибке клиент может обновить состояние через GET, чтобы восстановить актуальную revision.

Запасной `POST /api/sessions/:id/finish` принимает `{revision}` после закрытия неисправного WebSocket. Он добавляет сохранённый сервером черновик к текущему ответу, исключает неотвеченные вопросы и завершает интервью с частичным отчётом. Уже завершённая сессия возвращается без повторной генерации. После сбоя отчёта `POST /api/sessions/:id/report` повторяет генерацию для `ready`.

## События и лимиты

Бинарные сообщения браузера — PCM16 little-endian mono 16000 Гц, обычно 3200 байт (100 мс), максимум 6400 байт. Сервер ресемплирует вход до 44100 Гц и отправляет Base64 в облако. SpeechKit возвращает событие `audio_file` с полным MP3; нативный Realtime возвращает PCM16 mono 44100 Гц в `audio`.

| Событие сервера | Данные | Назначение |
| --- | --- | --- |
| `ready` | `sampleRate`, `outputSampleRate`, `outputFormat`, `maxDurationSeconds` | Настройки подтверждены облаком; можно начать микрофон |
| `session` | `session` | Актуальные история, revision, вопрос и состояние |
| `assistant_transcript` | `text`, `partial` | Каноническая реплика для озвучивания |
| `status` | `phase` | `thinking`, `speaking`, `listening` или `finishing` |
| `audio` | `audio`, `sampleRate` | Base64 PCM в нативном режиме |
| `audio_file` | `audio`, `mimeType` | Один полный MP3 вопроса в быстром режиме |
| `audio_done` | — | Закончилось аудио реплики |
| `speech_start`, `speech_stop` | — | Начало/конец речи по облачному VAD |
| `transcript` | `text`, `partial` | Расшифровка текущей реплики |
| `finishing` | — | Завершение всего интервью, отключение микрофона |
| `done` | `session`, `text` | Итоговая сессия; соединение закрывается |
| `error` | `message`, `session`, `text`, `partial` | Ошибка и доступное состояние для восстановления |

Команда браузера `{"type":"finish"}` завершает всё интервью, а не текущий ответ. Транспорт также понимает `cancel` для очистки и `cancel_audio` для отмены озвучивания; в нормальном UI отдельные кнопки для них не выводятся.

`server_vad` использует threshold 0.5 и silence_duration_ms 1200. По окончании транскрипции без ожидающих фраз сервер принимает ответ. Если пользователь продолжает после паузы, модель уже может готовить уточнение или новый вопрос. Во время серверной генерации следующий аудиоввод не принимается как новый ответ; следует ориентироваться на статус «Слушаю вас».

- Одно соединение — до 10 минут; лимит вызывает завершение интервью и отчёт.
- Облачный handshake — до 15 секунд; подтверждение конфигурации — до 18 секунд, клиентское подключение — до 20 секунд.
- При ручном завершении сервер ждёт текущую транскрипцию до 12 секунд, затем использует доступный текст; клиент ждёт завершение до 120 секунд.
- Максимум входного PCM — 19200000 байт, также проверяется передача в реальном времени с допуском около двух секунд.
- Очередь исходящего браузерного WebSocket — до 64000 байт; серверного upstream — до 256000 байт; обратного потока — до 2 МиБ. Переполнение завершает операцию с ошибкой.
- Клиентский PCM-плеер ограничивает очередь 30 секундами; поддерживает частоты 16, 22.05, 24, 44.1 и 48 кГц.
- Ответ с уточнением ограничен 4000 символами; при превышении требуется завершить интервью.

## Проверки и ограничения

На 17 ноября 2026 проверена новая непрерывная реализация:

- `npm run check`: 60 тестов прошли, production-сборка успешна; платные API не вызываются.
- `tests/realtime.test.mjs`: 13 тестов на конфигурацию и ключ, ресемплинг, пять автоматических вопросов в одном WebSocket, одно уточнение, досрочное завершение, финализацию текущей транскрипции, пустое интервью, допуск, повтор подключения после сбоя генерации и восстановление черновика. Облачный транспорт подменён.
- `tests/realtime-playback.test.mjs`: 7 тестов MP3-декодирования, отмены декодирования при перебивании, PCM, непрерывности очереди при поздних чанках, восстановления после underrun, прерывания и предела буфера с подменённым AudioContext.
- HTTP-тесты проверяют запасной `/finish`, частичный отчёт, завершение без ответов, повтор отчёта и проверку структурированного уточнения.

`npm run smoke:realtime` прошёл с настоящим облаком: два автоматических вопроса в одном WebSocket, потоковое аудио обеих реплик, синтетический микрофон 16 кГц, серверный ресемплинг, VAD, финальные транскрипции и завершение с частичным отчётом по двум ответам. Генератор вопросов, уточнений и отчёта в этом тесте подменён; персональные данные не использовались.

Физический микрофон, акустическое эхо, перебивание и качество английского произношения требуют ручного прогона на устройстве. Синтетическое аудио проверяет протокол, но не эти свойства. `npm run smoke:realtime` — отдельный платный тест: два автоматических раунда через локальный мост и настоящий речевой API в одном WebSocket. Синтетическое облачное аудио возвращается во вход PCM 16 кГц с темпом 100 мс/чанк; проверяются VAD, транскрипция и досрочное завершение. Генераторы вопросов, уточнений и отчёта подменены. Это не проверка браузера, физического микрофона или платной генерации отчёта.

Сессии находятся в памяти сервера и пропадают после его перезапуска. Необработанные аудиочанки после разрыва не восстанавливаются. Приложение не записывает речь на диск; поставщик получает историю/реплики и аудио микрофона. Хранение запросов в облаке настраивается отдельно. Realtime оплачивается отдельно от Chat Completions. Быстрое озвучивание дополнительно использует SpeechKit TTS; вопрос или уточнение выбирается одним LLM-запросом. Проект остаётся локальной демонстрацией без пользовательской авторизации и глобального лимита облачного бюджета.

## Быстрый старт озвучивания

`REALTIME_TTS=speechkit` — режим по умолчанию. Используется существующий `server/speech.mjs`, голос `TTS_VOICE` (по умолчанию `filipp`), скорость 1.0, `format=mp3`. Требуются `TTS_ENABLED=true` и роль `ai.speechkit-tts.user`. Полный MP3 передаётся одним `audio_file {audio: Base64, mimeType: "audio/mpeg"}`. Браузер вызывает `decodeAudioData` и воспроизводит одну реплику одним AudioBufferSourceNode. Перебивание и завершение отменяют запрос синтеза; поздние ответы и результаты декодирования игнорируются. Настройки Realtime подтверждаются один раз; между вопросами быстрый синтез не ждёт `session.updated` и завершения отменённого ответа речевой модели. Автоматические ответы Realtime отменяются и не озвучиваются.

`REALTIME_TTS=native` возвращает озвучивание через речевую модель Realtime, голос `REALTIME_VOICE`. При отключённом SpeechKit (`TTS_ENABLED=false`) также используется нативный путь. Ошибки доступа к включённому SpeechKit не подменяются другим синтезом: показывается ошибка с возможностью повторить подключение или завершить интервью.

Вопросы и следующие шаги ограничены 600 выходными токенами; отчёт сохраняет лимит 3000. `npm run smoke:realtime` выводит время от появления текста вопроса до первого аудиочанка. Это замер синтетического сценария с подменённым генератором вопросов, без задержки YandexGPT и физического воспроизведения. Устойчивого SLA из одного замера не следует.

Замер 17 ноября 2026: успешный двухраундовый smoke быстрого пути дал 225 и 110 мс от текста до первого PCM-чанка в предыдущем варианте (его заменил MP3 после жалоб на треск). Нативный путь в предыдущем запуске дал 7754 и 13795 мс; отдельный прямой запрос SpeechKit — 1425 мс. Это отдельные запуски с разным состоянием облака, а не контролируемый бенчмарк. Объединённый `nextTurn` на синтетическом ответе был проверен настоящим YandexGPT: 601 мс, один запрос.

В быстром режиме `ready.outputFormat` равен `mp3`, а `outputSampleRate` равен `null`: реальную частоту определяет MP3-декодер. Нативный режим по-прежнему использует `pcm16` и 44100 Гц. Smoke дополнительно синтезирует одну PCM-фразу для тестового микрофона: всего одна Realtime-сессия и три TTS-запроса в быстром режиме. Качество на реальном устройстве проверяется отдельно.

После перехода быстрого режима на единый MP3 двухраундовый облачный smoke прошёл: 295 и 244 мс от текста до получения MP3. Декодирование и физическое воспроизведение в эти интервалы не входят.
