# Сервер

Сервер — Node.js-приложение на встроенном `node:http`, без Express. Он хранит интервью, проверяет запросы браузера, обращается к облачным адаптерам и раздаёт собранный фронтенд.

Связанные документы: [обзор проекта](../README.md), [фронтенд](FRONTEND.md), [Yandex AI Studio](YANDEX-AI-STUDIO.md), [Realtime](REALTIME.md).

## Модули

| [`server/index.mjs`](../server/index.mjs) | Создаёт адаптеры LLM, TTS, STT и Realtime, собирает приложение, запускает сервер на `127.0.0.1` |
| [`server/app.mjs`](../server/app.mjs) | HTTP API, память сессий, валидация, блокировки, статические файлы и подключение WebSocket |

`createApp(provider, options)` принимает адаптеры извне. В тестах и smoke-проверках это позволяет подменять облако, запускать mock или использовать локальный gRPC-сервер.

## Запуск

`npm run dev` запускает два процесса через [`scripts/dev.mjs`](../scripts/dev.mjs): Node.js с `--watch` и Vite. Backend читает `.env` через `--env-file-if-exists`; Vite проксирует `/api`, включая WebSocket, на `http://127.0.0.1:3001`.

В production-сценарии `npm run build` создаёт `dist/`, а `npm start` запускает один Node.js-процесс. `PORT` по умолчанию равен 3001. Значение `PORT` не меняет автоматически dev-proxy. Сервер слушает только loopback; это не настройка публичного хостинга.

## Сессия интервью

Сессии находятся в `Map` внутри `createApp`. Публичное представление:

```json
{
  "id": "uuid",
  "level": "Junior",
  "mode": "yandex",
  "interactionMode": "voice",
  "total": 5,
  "revision": 0,
  "status": "active",
  "turns": [{ "question": "Текст вопроса", "answer": null }],
  "report": null
}
```

`mode` — облачный или mock-провайдер. `interactionMode` — режим общения при создании сессии; последующие переключения UI хранятся в браузере и не обновляют это поле на сервере.

Внутренние поля `updated`, `busy`, `speechBusy`, `sttBusy` и `realtimeBusy` не отдаются клиенту. Они нужны для срока хранения и ограничения одновременных операций. `sttBusy` и `realtimeBusy` во время распознавания хранит ссылку на WebSocket, чтобы завершение старого соединения не снимало блокировку нового.

### Состояния обычных режимов

```text
POST /sessions → active
ответы 1–4     → active + следующий вопрос
ответ 5        → ready
успешный отчёт → completed
```

При создании сразу генерируется первый вопрос. Если генерация не удалась, новая сессия удаляется.

Ответ сначала записывается в копию истории. Для первых четырёх ответов сервер получает следующий вопрос и только после успеха сохраняет весь ход. Ошибка генерации оставляет исходную сессию без текущего ответа. Пятый ответ переводит её в `ready` без вызова LLM.

Отчёт создаётся отдельным запросом. При ошибке пять ответов остаются сохранёнными; запрос отчёта можно повторить. Уже готовый отчёт возвращается повторно без новой генерации, в том числе при старой `revision` в запросе.

В Realtime ответы и переходы сохраняются из WebSocket автоматически, отчёт создаётся по окончании разговора; подробности ниже.

### Revision и блокировки

Каждое успешное сохранение ответа или отчёта увеличивает `revision`. Клиент передаёт последнюю известную версию; при несовпадении сервер возвращает 409. GET сессии помогает восстановить актуальное состояние, например после потери сетевого ответа.

`busy` блокирует конкурентные изменения интервью. Активный STT блокирует отправку ответа, получение отчёта и удаление сессии. TTS не запускается параллельно с другим TTS или STT той же сессии. STT не запускается при занятом интервью или TTS. Realtime требует свободную активную сессию и блокирует TTS, STT, отправку ответа, отчёт и удаление до закрытия соединения. Общей очереди и глобального ограничения облачных запросов нет.

## HTTP API

Для POST ожидается объект JSON и `Content-Type: application/json`. Размер тела — до **24000 байт**, а не символов.

| Метод и путь | Вход | Успех |
| --- | --- | --- |
| `GET /api/health` | — | 200: `{mode, ready, speech: {enabled, recognitionEnabled, realtimeEnabled}}` |
| `POST /api/sessions` | `{level, interactionMode?}` | 201: сессия с первым вопросом |
| `GET /api/sessions/:id` | — | 200: текущее публичное состояние |
| `POST /api/sessions/:id/answers` | `{answer, revision}` | 200: обновлённая сессия |
| `POST /api/sessions/:id/finish` | `{revision}` | 200: досрочно завершённая Realtime-сессия с отчётом либо `report: null`, если ответов нет |
| `POST /api/sessions/:id/report` | `{revision}` | 200: сессия с отчётом |
| `DELETE /api/sessions/:id` | — | 200: `{deleted: true}` |
| `POST /api/speech/synthesize` | `{sessionId, questionNumber}` | 200: бинарный MP3, `audio/mpeg` |

Уровень — `Intern`, `Junior`, `Middle` или `Senior`. `interactionMode` — `voice`, `text` либо `realtime`; без него сервер выбирает `text`. UI по умолчанию выбирает голосовой режим самостоятельно.

Ответ кандидата должен быть непустой строкой до 4000 символов; пробелы по краям удаляются перед сохранением. Для TTS номер вопроса начинается с 1 и должен указывать на существующий вопрос. Произвольный текст от клиента для синтеза не используется: сервер берёт вопрос из своей истории.

`ready: true` в health означает, что сервер запущен. Флаги речи отражают конфигурацию адаптеров, а не успешную проверку облачных прав.

## Протокол распознавания

Подключение:

```text
ws://127.0.0.1:<PORT>/api/speech/recognize?sessionId=<id>&revision=<revision>
```

WebSocket требует допустимый `Origin`, существующую неистёкшую сессию, статус `active`, актуальную revision и отсутствие конфликтующей операции. При отказе handshake получает 403, 404, 409 или 503. gRPC-соединение создаётся после допуска WebSocket.

Клиент передаёт бинарные чанки **mono PCM16 little-endian, 16000 Гц**. Обычный чанк — 3200 байт (100 мс), максимум сообщения — 6400 байт. Размер аудио должен быть ненулевым и чётным.

Для завершения клиент отправляет текстовый JSON:

```json
{"type":"finish"}
```

| Событие сервера | Данные | Значение |
| --- | --- | --- |
| `ready` | `sampleRate`, `maxDurationSeconds` | Мост готов принимать аудио; это ещё не подтверждение облачных прав |
| `transcript` | `text`, `partial` | Подтверждённые фразы и текущая изменяемая гипотеза |
| `finishing` | — | Ввод завершается, ожидаются последние результаты |
| `done` | `text`, `partial` | Поток распознавания завершён |
| `error` | `message`, `text`, `partial` | Ошибка с уже полученным текстом |

Финальные фразы собираются по `finalIndex`. `finalRefinement` заменяет нужную фразу нормализованной версией, не добавляя её повторно. STT не записывает ответ в `turns` и не меняет revision. После проверки текста браузер отправляет обычный HTTP-запрос `/answers`.

### Ограничения потока

- Одна запись — до 120 секунд; после лимита сервер начинает завершение.
- Отсутствие аудиочанков 15 секунд — ошибка. Это таймаут транспорта, а не детектор тишины: микрофон может продолжать передавать PCM с тишиной.
- Ожидание финальных результатов после завершения — до 12 секунд.
- Объём — до 3840000 байт, плюс проверка, что аудио не отправляется намного быстрее реального времени.
- Остаточная очередь сервера — до 64000 байт. При заполнении writable-буфера gRPC WebSocket приостанавливается; сообщения, уже декодированные из того же TCP-пакета, остаются в ограниченной очереди до `drain`.
- Расшифровка ограничена 4000 символами. Закрытие клиентского соединения отменяет gRPC-вызов и освобождает блокировку.

## Непрерывное Realtime-интервью

Путь `/api/speech/realtime?sessionId=<id>&revision=<revision>` открывает один браузерный WebSocket на всё интервью. Допуск проверяет Origin, TTL, revision, статус и блокировки. Ключ остаётся на сервере. Микрофон и воспроизведение активны между вопросами; после VAD-паузы сервер автоматически сохраняет ответ, одним вызовом `provider.nextTurn` выбирает уточнение, следующий вопрос или завершение. Готовый текст по умолчанию озвучивается через единый MP3 SpeechKit; `REALTIME_TTS=native` возвращает нативное аудио Realtime.

Не более пяти основных вопросов и одного уточнения на каждый. Realtime отвечает за голосовой транспорт; очередность, сохранение истории, revision и оценки контролирует сервер. После пятого ответа либо команды `finish` создаётся отчёт. Досрочный отчёт содержит 1–5 оценок, неподтверждённый вопрос без ответа не оценивается. Если ответов нет, итог — `completed` и `report: null`. Ошибка отчёта оставляет `ready`, чтобы запросить `/report` повторно.

Пока WebSocket активен, `realtimeBusy` запрещает конфликтующие HTTP-операции. При сбое соединение закрывается, сохранённая часть остаётся в памяти. После освобождения блокировки `POST /api/sessions/:id/finish` с последней revision добавляет серверный черновик к текущему ответу, удаляет неотвеченные вопросы и завершает интервью по сохранённой части. Повтор для уже завершённой сессии возвращает её без новой генерации. Во время исправного соединения завершение передаётся командой WebSocket, а не этим запасным HTTP-маршрутом.

Вход браузера — PCM16 mono 16 кГц; сервер ресемплирует до PCM16 44.1 кГц и отправляет Base64. Обратный поток содержит MP3 (`audio_file`) в быстром режиме или PCM16 44.1 кГц (`audio`) в нативном. Полные события, конфигурация, ограничения и проверки — в [REALTIME.md](REALTIME.md).

## Синтез и статические файлы

TTS собирает MP3 на сервере целиком, затем отдаёт его браузеру. Ответ содержит `Cache-Control: no-store`. Повтор в интерфейсе использует аудио из памяти компонента; серверного аудиокеша нет. Если браузер отменяет незавершённую загрузку, закрытие HTTP-ответа вызывает `AbortController.abort()` для облачного запроса.

За пределами `/api/` сервер обслуживает GET и HEAD из `dist/`. `/` соответствует `index.html`; произвольные отсутствующие пути не переписываются на SPA-страницу. Проверяется, что путь остаётся внутри каталога сборки.

## Ошибки и хранение

HTTP-ошибка имеет форму `{error: string}`. Ошибки `AppError` получают свой статус и безопасный текст; неожиданные исключения становятся 500 с общей формулировкой. Сырой ответ облака не отправляется браузеру.

Основные статусы: 400 — валидация; 403 — Origin; 404 — сессия/путь; 409 — версия/занятость/состояние; 413 — тело слишком большое; 415 — неподходящий Content-Type; 429 — лимит сессий или TTS; 502/504 — облачная ошибка/недоступность; 503 — выключенный речевой адаптер. Ошибки квот YandexGPT отображаются через 502, а TTS — через 429.

HTTP допускает запрос без Origin, но проверяет его, когда заголовок передан. WebSocket требует Origin. Разрешены `http://<Host>` и фиксированный dev-адрес `http://127.0.0.1:5173`. Это локальная проверка источника, не аутентификация пользователей.

В памяти допускается до 100 сессий. TTL — 2 часа с создания или успешного изменения ответа/отчёта. Очистка происходит при следующем HTTP API-запросе и пропускает занятые сессии. GET, TTS и STT не обновляют `updated`; Realtime обновляет его при сохранении ответов; WebSocket дополнительно проверяет срок при handshake. После перезапуска память пуста. Для публичного сервиса нужны отдельные решения по авторизации, хранению и ограничению расходов.
