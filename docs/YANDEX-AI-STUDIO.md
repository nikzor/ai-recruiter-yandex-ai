# Интеграция с Yandex AI Studio

Приложение использует четыре возможности облака: генерацию текста, синтез речи, распознавание речи и отдельный Realtime API для потокового голосового взаимодействия. Все облачные обращения выполняет Node.js-сервер; браузер общается с ним по HTTP и WebSocket.

Документ описывает текущий код на 17 ноября 2026. В обычном голосовом режиме озвучивание восстановлено на **SpeechKit TTS v1 / filipp / скорость 1.0**. LiveTTS и словарь произношения из предыдущих экспериментов не входят в действующую интеграцию.

Связанные документы: [обзор проекта](../README.md), [сервер](SERVER.md), [фронтенд](FRONTEND.md), [Realtime](REALTIME.md).

## Используемые сервисы и модули

| Задача | Облачный API | Модуль проекта | Транспорт и библиотеки |
| --- | --- | --- | --- |
| Генерация вопросов и отчёта | YandexGPT, OpenAI-совместимый Chat Completions | [`server/provider.mjs`](../server/provider.mjs) | HTTPS, встроенный Node.js `fetch` |
| Озвучивание вопроса | SpeechKit TTS REST API v1 | [`server/speech.mjs`](../server/speech.mjs) | HTTPS, `fetch`, URLSearchParams, MP3 |
| Распознавание ответа | SpeechKit STT gRPC API v3 | [`server/stt.mjs`](../server/stt.mjs) | TLS/gRPC, `@grpc/grpc-js`, `@grpc/proto-loader` |
| Потоковый голосовой диалог | Yandex Realtime API | [`server/realtime.mjs`](../server/realtime.mjs), [`server/realtime-socket.mjs`](../server/realtime-socket.mjs) | WebSocket, `ws`, PCM16, серверный ресемплинг |
| Приём аудио из браузера | Собственный WebSocket, не API SpeechKit | [`server/stt-socket.mjs`](../server/stt-socket.mjs) | Пакет `ws`, мост к gRPC |

OpenAI SDK и Yandex Cloud SDK не установлены. Совместимость с OpenAI здесь означает формат Chat Completions, а не зависимость от пакета `openai`. Преобразование аудио выполняется в браузере через AudioWorklet и собственный PCMEncoder.

```text
Вопросы / отчёт: браузер → HTTP API сервера → YandexGPT → JSON
Озвучивание:    браузер → HTTP API сервера → SpeechKit TTS → MP3
Ответ голосом:  микрофон → AudioWorklet → WebSocket сервера → SpeechKit STT gRPC
Расшифровка:    SpeechKit STT → сервер → WebSocket → черновик в браузере
Realtime:      микрофон ↔ WebSocket сервера ↔ Realtime API (аудио и транскрипты)
Обычный режим: черновик → HTTP /answers → серверная история → YandexGPT
Realtime:      пауза → серверная история → YandexGPT nextTurn → новое аудио
```

## Доступ и конфигурация

Для облачного режима нужны оплачиваемый каталог Yandex Cloud, сервисный аккаунт с нужными ролями и API-ключ с подходящими областями действия. Назначение роли и scope ключа — отдельные настройки: доступ к генерации текста сам по себе не подтверждает доступ к речи.

| Возможность | Роль сервисного аккаунта | Область действия ключа |
| --- | --- | --- |
| YandexGPT | `ai.languageModels.user` | `yc.ai.foundationModels.execute` используется в официальном примере structured output |
| TTS | `ai.speechkit-tts.user` | `yc.ai.speechkitTts.execute` либо подходящая общая `yc.ai.foundationModels.execute` |
| Realtime | `ai.models.user` | `yc.ai.foundationModels.execute` |
| STT | `ai.speechkit-stt.user` | `yc.ai.speechkitStt.execute` либо подходящая общая `yc.ai.foundationModels.execute` |

Общая область `yc.ai.foundationModels.execute` описана в [справочнике API-ключей](https://yandex.cloud/ru/docs/iam/concepts/authorization/api-key); проверяйте фактические разрешения созданного ключа. Для генерации текста настройка выше соответствует [официальному примеру JSON Schema](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/generation/completions-structured).

Для Realtime официальная [инструкция создания голосового агента](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/agents/create-voice-agent) указывает отдельную роль `ai.models.user` и scope `yc.ai.foundationModels.execute`. Рабочий ключ для Chat Completions или SpeechKit ещё не подтверждает доступ к Realtime.

Переменные читает сервер из `.env`:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `AI_MODE` | `mock` | `mock` либо `yandex`; только явный `yandex` включает облако |
| `API_KEY` | — | Основной API-ключ облачных адаптеров |
| `YANDEX_API_KEY` | — | Запасное имя ключа; используется при пустом/отсутствующем API_KEY |
| `YANDEX_FOLDER_ID` | — | Каталог для URI модели и заголовка Chat Completions |
| `YANDEX_MODEL` | `yandexgpt-5.1` | Имя модели без префикса `gpt://<folder_id>/` |
| `TTS_ENABLED` | включено при `AI_MODE=yandex` и наличии ключа | Только строка `false` явно выключает TTS |
| `TTS_VOICE` | `filipp` | Голос TTS v1 |
| `STT_ENABLED` | включено при `AI_MODE=yandex` и наличии ключа | Только строка `false` явно выключает STT |
| `REALTIME_ENABLED` | включено при `AI_MODE=yandex`, ключе и Folder ID | Только строка `false` явно выключает Realtime |
| `REALTIME_MODEL` | `speech-realtime-deepseek-v4-flash` | Имя либо полный URI речевой модели Realtime |
| `REALTIME_TTS` | `speechkit` | Быстрый SpeechKit MP3; `native` — нативное аудио Realtime |
| `REALTIME_VOICE` | `filipp` | Голос Realtime, независимо от `TTS_VOICE` |
| `PORT` | `3001` | Локальный сервер приложения, не облачный endpoint |

В `yandex` отсутствие ключа или Folder ID не позволяет создать LLM-адаптер и запустить приложение. TTS/STT/Realtime не проверяют права заранее; флаги health описывают конфигурацию. Параметры `TTS_ROLE` и `TTS_SPEED` сейчас не используются.

Ключ остаётся на сервере, не включается в клиентскую сборку и передаётся только в заголовках/метаданных облачных запросов. `.env` исключён из Git. В cloud-режиме провайдер получает историю интервью, озвучиваемые вопросы и записанное аудио; политика хранения запросов в облаке настраивается отдельно и не управляется кодом проекта.

## YandexGPT: вопросы и оценка

Endpoint:

```text
POST https://ai.api.cloud.yandex.net/v1/chat/completions
```

Заголовки адаптера:

```text
Authorization: Api-Key <server_key>
OpenAI-Project: <folder_id>
Content-Type: application/json
```

В запросе задаются модель `gpt://<folder_id>/<YANDEX_MODEL>`, `temperature: 0.3`, `max_tokens: 600` для вопросов и следующего шага, `3000` для отчёта, `stream: false` и `response_format` типа `json_schema`. Используются схемы `interview_question`, `interview_next_turn` и `interview_report` (отдельный `interview_followup` оставлен для совместимости). Поддержка structured output описана в [документации Chat Completions](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/generation/completions-structured).

### Формирование контекста

Сервер собирает сообщения заново для каждого запроса:

1. System prompt: роль учебного интервьюера Flutter, уровень и требования к сложности, русский язык и JSON-формат. Ответы кандидата обозначены недоверенными данными.
2. История из серверной сессии: вопросы как `assistant`, полученные ответы как `user`.
3. Инструкция текущей операции: следующий вопрос, решение об уточнении либо итоговый отчёт.

Отдельного облачного thread/assistant и серверной памяти диалога у провайдера проект не создаёт. Источник истории — локальная сессия. Клиент не передаёт готовый массив messages, system prompt или выбор провайдера.

Вопрос №1…5 соответствует теме из `questions.mjs`: Dart, виджеты, состояние, данные, качество. В промпт добавляется пример сложности из банка выбранного уровня. Модель должна учесть ответы и не повторять вопросы. В обычных режимах адаптация идёт внутри фиксированного сценария из пяти тем. В Realtime `provider.nextTurn` одним запросом выбирает уточнение, новый вопрос или завершение. Сервер проверяет схему `{action: "followup" | "question" | "finish", question: string}`, лимит пяти тем и одного уточнения. Не более одного уточнения на основной вопрос; достаточный ответ или отказ ведут к следующей теме. Уточнение и ответ учитываются в истории и итоговой оценке основного вопроса.

### Проверка результата

Вопрос принимается, если модель завершила генерацию с `finish_reason: stop`, вернула JSON и непустую строку `question` длиной до 4000 символов.

Отчёт содержит:

| Поле | Содержание |
| --- | --- |
| `summary` | Общая обратная связь |
| `strengths` | Сильные стороны |
| `gaps` | Пробелы |
| `recommendations` | Рекомендации |
| `assessments` | От 1 до 5 записей `{questionNumber, score, rationale}` по обсуждённым вопросам |

После JSON Schema сервер дополнительно проверяет типы, непустые строки, длины, количество оценок по фактическому числу вопросов (1–5) и их порядок, целые баллы 0–4. Списки допускают до 10 элементов. Итоговый `score` вычисляет сервер, а не модель:

```text
round(sum(оценок) / (число обсуждённых вопросов * 4) * 100)
```

Шкала в промпте: 0 — неверно или нет ответа по сути; 1 — фрагментарно; 2 — частично верно; 3 — соответствует уровню; 4 — полно, с обоснованием и примером. Это учебная обратная связь; в промпте запрещены выводы о найме. Отдельных платных оценок после каждого раунда нет: разбор создаётся в конце.

В полном обычном интервью без повторов нужно шесть LLM-запросов: первый вопрос при создании сессии, четыре следующих после ответов и один отчёт. В Realtime следующий вопрос и решение об уточнении объединены в один запрос. После пятого ответа без уточнения возможен один запрос для выбора уточнения либо завершения; после ответа на уточнение пятого вопроса сразу создаётся отчёт. При досрочном завершении отчёт оценивает только обсуждённые вопросы и указывает ограниченность результата. Без ответов отчёт не создаётся, сессия завершается с `report: null`.

Облачный запрос использует сигнал таймаута 45 секунд. Ошибки доступа, квот, неполный/невалидный ответ не подменяются mock-результатом; автоматических повторов нет.

## SpeechKit TTS: вопрос в аудио

Endpoint:

```text
POST https://tts.api.cloud.yandex.net/speech/v1/tts:synthesize
```

`server/speech.mjs` отправляет URL-encoded тело с полями `text`, `lang=ru-RU`, `voice=filipp` (или TTS_VOICE), `format=mp3`, `speed=1.0`. Авторизация — `Api-Key`; Folder ID для сервисного аккаунта в этот запрос не добавляется. Параметры и ответ описаны в [TTS REST API v1](https://aistudio.yandex.ru/ru/docs/speechkit/tts/request).

Текст берётся из серверного вопроса без транслитерации, словаря и изменения английских названий. Сервер проверяет длину до 4000 символов и размер URL-encoded тела до 15000 байт. Полученный ответ должен иметь аудиотип, быть непустым и укладываться в 2 МиБ.

MP3 сначала собирается сервером, затем возвращается браузеру с `audio/mpeg`. До браузера потокового воспроизведения по предложениям нет. Таймаут — 30 секунд; закрытие клиентского HTTP-ответа отменяет облачный fetch.

HTTP 401/403 превращаются в понятную ошибку настройки доступа, 429 — в сообщение о лимите. Подробности ответа провайдера не раскрываются. Пользователь может повторить запрос или продолжить текстом. Повтор в том же экземпляре плеера использует уже загруженный MP3; повторная загрузка после смены вопроса/режима или перезагрузки может стать новым платным синтезом.

## SpeechKit STT: голос в текст

Прямой потоковый API SpeechKit использует **gRPC v3**, а не WebSocket. Собственный WebSocket нужен для соединения браузера с Node.js. Протокол и рекомендация v3 для новых проектов приведены в [документации потокового распознавания](https://aistudio.yandex.ru/ru/docs/speechkit/stt/streaming).

gRPC-клиент соединяется по TLS с `stt.api.cloud.yandex.net:443` и вызывает `speechkit.stt.v3.Recognizer/RecognizeStreaming`. В metadata передаётся `authorization: Api-Key <server_key>`. Folder ID для сервисного аккаунта не передаётся. Deadline вызова — 140 секунд; собственный лимит записи приложения — 120 секунд.

### Protobuf и библиотеки

`@grpc/proto-loader` загружает локальный `server/proto/recognizer.proto`, а `@grpc/grpc-js` создаёт клиент из package definition. `stt.proto` взят без изменений из официального `yandex-cloud/cloudapi`; commit, лицензия и происхождение записаны в [server/proto/SOURCE.md](../server/proto/SOURCE.md). Локальный `recognizer.proto` содержит только необходимый streaming RPC с исходными сообщениями и путём метода. Во время запуска ничего не скачивается и не генерируется.

### Обмен с облаком

Первым сообщением уходит `sessionOptions`:

| Параметр | Значение |
| --- | --- |
| Модель | `general` |
| Режим обработки | `REAL_TIME` |
| Кодирование | `LINEAR16_PCM` |
| Частота и каналы | 16000 Гц, 1 канал |
| Язык | `WHITELIST`, `ru-RU` |
| Нормализация | `TEXT_NORMALIZATION_ENABLED` |

Затем передаются `chunk.data` с PCM из браузера. Сервер обрабатывает:

- `partial` — изменяемую текущую гипотезу;
- `final` — подтверждённую фразу с индексом;
- `finalRefinement.normalizedText` — нормализованную замену фразы по её индексу.

В браузер отправляются накопленный финальный текст и текущая гипотеза. По команде завершения сервер закрывает только вход gRPC (`end`), продолжая читать последние результаты. Закрытие соединения пользователем отменяет вызов (`cancel`); после gRPC-статуса клиент закрывается.

Пауза в речи может завершить отдельную фразу в SpeechKit, но не отправляет ответ интервью автоматически. Пользователь заканчивает запись, проверяет расшифровку и отправляет её через HTTP. Именно подтверждённый текст становится следующим сообщением YandexGPT. Подробные лимиты, события WebSocket и управление очередью описаны в [SERVER.md](SERVER.md#протокол-распознавания).

## Realtime: аудио в обе стороны

Отдельный режим «Диалог Realtime» использует endpoint:

```text
wss://ai.api.cloud.yandex.net/v1/realtime/openai?model=gpt://<folder_id>/speech-realtime-deepseek-v4-flash
```

Авторизация серверного WebSocket — `Authorization: Api-Key <server_key>`. Браузер подключается только к собственному серверу и ключа не получает. API и модель описаны в [документации Realtime](https://aistudio.yandex.ru/ru/docs/ai-studio/realtime/).

Вместо ручной отправки расшифровки Realtime ведёт непрерывное интервью в одном браузерном WebSocket. Микрофон включается при старте сессии; VAD завершает реплики по паузе. Сервер сохраняет ответы, запрашивает у YandexGPT уточнение либо следующий основной вопрос и отправляет текст напрямую в SpeechKit TTS для быстрого озвучивания. На основной вопрос допускается одно уточнение. После пяти вопросов автоматически создаётся отчёт; кнопка «Завершить интервью» готовит отчёт по пройденной части.

Канонические вопросы, состояние, лимит пяти тем и итоговая оценка остаются на сервере. В нативном режиме речевая модель получает инструкцию произнести текущую реплику. В быстром режиме готовый текст озвучивает SpeechKit. Речевая модель самостоятельно не управляет интервью и не выставляет баллы. Голос можно перебить; новые ответы принимаются без редактора и ручного подтверждения. SpeechKit STT при этом не вызывается. По умолчанию используется SpeechKit TTS v1 с выдачей одного MP3 на вопрос; `REALTIME_TTS=native` возвращает аудио Realtime. Для быстрого пути нужны права TTS.

Браузер передаёт PCM16 mono 16 кГц; сервер преобразует его в PCM16 44.1 кГц и Base64 для `input_audio_buffer.append`. `response.output_audio.delta` возвращается в браузер для потокового воспроизведения. Транскрипции `conversation.item.input_audio_transcription.delta/completed` сохраняются в серверном состоянии, а события с публичной сессией обновляют UI. После сбоя можно подключиться снова или завершить сессию через HTTP; тихого перехода в другой режим нет.

Realtime оплачивается отдельно от Chat Completions. Точный протокол, VAD, лимиты, восстановление и результаты проверок — в [REALTIME.md](REALTIME.md).

## Mock и обработка сбоев

При `AI_MODE=mock` LLM-адаптер возвращает банк вопросов и фиксированные 2/4 за каждый ответ. TTS, STT и Realtime выключены. Наличие ключа само по себе не переводит приложение в облако.

В `yandex` нет автоматического перехода в mock и скрытых повторов. В обычных режимах ошибка генерации следующего вопроса не сохраняет текущий ответ; ошибка отчёта не удаляет историю. В Realtime сохранённые ответы остаются в сессии; состояние `ready` позволяет повторить отчёт. В обычном голосовом режиме сбой речи не мешает ответить с клавиатуры; полученную часть текста можно проверить. В Realtime после сбоя доступны повторное подключение и завершение по сохранённой части, без редактора и переключения режима.

Аудио обычного интервью не записывается на диск приложением. История находится в памяти Node.js; обычный черновик и аудиокеш — в памяти вкладки. Realtime также хранит на сервере полученную расшифровку текущего ответа для восстановления после сбоя. Исключение — явно запускаемые smoke-скрипты: TTS-проверка сохраняет синтетический MP3 во временный каталог.

## Проверка интеграции

`npm run check` использует подменённый transport и локальные серверы, не тратит облачный бюджет. Проверяются формат LLM/TTS-запросов, валидация ответов, gRPC/protobuf, WebSocket STT и Realtime, PCM-плеер, ограничения, таймауты и отмена.

Реальные smoke-команды запускаются отдельно:

- `smoke:yandex` — полное интервью на синтетических ответах; шесть LLM-вызовов, затем проверка восстановления и удаление сессии.
- `smoke:tts` — один синтез вопроса с английскими Flutter-терминами в MP3.
- `smoke:realtime` — два автоматических раунда в одном WebSocket через локальный серверный мост и настоящее облако: потоковое аудио, синтетический PCM-вход 16 кГц, VAD, транскрипции, досрочное завершение. Генератор вопросов, уточнений и отчёта подменён; физический микрофон не участвует.
- `smoke:stt` — TTS генерирует русскую учебную фразу в LPCM 16 кГц; скрипт отправляет её по собственному WebSocket с темпом 100 мс/чанк, проверяет partial и финальный текст. LLM в этом сценарии mock, физический микрофон не используется.

Успешный API-вызов проверяет интеграцию, но не подтверждает естественность голоса, точность произношения английских терминов и объективность оценивания. Для этого нужны отдельные прослушивания и наборы эталонных ответов.
